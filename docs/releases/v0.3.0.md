# phobos v0.3.0

This minor release adds native Forge-X compatibility through the explicit
`--compat forge-x` startup profile. Existing installations keep the default
`moonraker` profile until their launcher changes. Zig 0.17.0, SQLite 3.54.1
and the Moonraker reference pin `900848584374` are unchanged.

## Changes

Forge-X uploads extract selected G-code from `.gcode.3mf` archives with bounded
ZIP validation, optional MD5/header checks and upload progress dialogs. The
converted file continues through normal metadata, file events and print/queue
handling. Direct, uploaded, OctoPrint and queued print starts share the stock
Forge-X leveling-macro selection. Explicit object queries can request hidden
objects while object discovery remains filtered.

Native timelapse loads from `[timelapse]` in either profile. It supports bounded
HTTP camera capture, persisted settings, macro acknowledgements, hyperlapse,
final frames, cancellation and ZIP export. An installed FFmpeg renders MP4
and JPEG previews through a bounded worker. See [timelapse](../TIMELAPSE.md)
for configuration, resource limits and remaining hardware checks.

Service allowlists load from `moonraker.asvc`. The Forge-X profile verifies
managed services before Git updates and respects its automatic-refresh skip
marker. Feather status refresh and update progress/failure messages retain
the active request token. These features run natively; no Python component
loader or extension runtime is introduced.

The separate [Forge-X tracker](../api/FORGE_X.md) records its API baseline,
behavioral differences and verification limits. The [README](../../README.md#run-on-a-forge-x-printer)
now covers architecture selection, checksums, chroot execution, the launcher,
database backups and rollback on the printer.

## Verification

The implementation passes the complete Debug, ReleaseSafe and ReleaseFast
suites: 1,803 passed, one gated real-Klippy skip and zero failures per mode,
including 342 bounded fuzz tests. All 114 Python tooling tests and four
build-policy tests pass. Native FFmpeg fixtures encode/decode video and check
the preview; upload fixtures cover multipart ordering and atomic publication.
Update tests use injected runners and owned local repositories.

Registration coverage is 123/123 paths, 130/130 RPC methods and 27/27 notifications
against upstream, and 121/121 paths, 129/129 methods and 28/28 notifications
against Forge-X. Both source baselines have no drift. These counts establish
registered names; they do not prove every behavior on physical hardware.

An ARM32 probe inside the real Forge-X chroot returned ready state, heater/print
status and directory capacity on loopback port 7126. It was stopped afterward.
The release workflow checks all seven static Linux profiles and native x86-64
and AArch64 suites before publishing. Production deployment verification is
recorded separately in [provenance](../PROVENANCE.md).

Existing [performance](../PERFORMANCE.md) and [memory](../MEMORY.md) results
remain explicitly measured v0.2.3 comparisons. No v0.3.0 performance gain is
claimed without new measurements.

## Retained behavior and limits

API 1.5.0 and software version `phobos` identify this implementation; Forge-X's
API 1.4.0 is a separate reference. Python version fields remain a stub. Missing
CAN interfaces return an empty discovery list. Optional components remain
available when configured. Host reboot and shutdown remain no-ops; package
execution requires an injected runner. Full Jinja2, real LDAP and real Apprise
remain outside scope; `klipper_estimator` requires an injected shell.

Real camera optics, parked motion, stock macro/UI interaction, managed updates
and third-party integrations still need dedicated hardware/integration checks.
The Forge-X profile does not make those workflows fixture-proven. No board or
Klipper restart is required to replace the API daemon.
