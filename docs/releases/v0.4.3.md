# phobos v0.4.3

This patch release stops a second print start from reaching Klipper while the
first start is still opening the virtual SD card. [v0.4.2](v0.4.2.md) returned
Klipper's `SD busy` text. The console line in this report was that second start.

## Changes

An upload of `name.gcode.3mf` with print requested extracts `name.gcode` and
sends `SDCARD_PRINT_FILE` for it. A client that then starts the original
archive name sends a second `SDCARD_PRINT_FILE` before `print_stats` leaves
its previous state. Klipper refuses that command because the virtual SD timer
is already running, and the console shows `!! SD busy` next to a print that
did start.

In Forge-X compatibility, a start named `name.gcode.3mf` prints the extracted
`name.gcode` when that file is in the gcodes directory and the archive is not.
A start of a file accepted in the previous two seconds, or of the archive it
was extracted from, returns HTTP 409 `Printer is busy` and sends nothing to
Klipper. A start while `print_stats` is `printing` or `paused` does the same.
A later print of the same file, after that window, is sent normally.

## Verification

The test suite passes in Debug, ReleaseSafe, and ReleaseFast: 1,809 passed,
one gated real-Klippy skip, zero failures, and 343 bounded fuzz tests per mode.
A new test starts `bracket.gcode` and then `bracket.gcode.3mf`. The second
response is HTTP 409 and Klipper is not called again.

The printer log that showed the pair of commands was taken from an AD5M running
phobos. This build has not been installed there.
